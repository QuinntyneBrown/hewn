# L2 - Detailed Requirements

> Status: DRAFT v1.
>
> **Terms.** A **direction** is a human instruction to build a new product (*product direction*) or to add a feature to an existing product (*feature direction*). A **run** is one execution of one stage for one direction. An **increment** is one backlog item delivered by stage 10. A **worker** is a process that runs agents.
>
> **Working assumptions** (change them and the affected L2s change):
> - Users sign in with GitHub. There are two roles: **Owner** (gives direction, can stop work) and **Viewer** (read-only).
> - The Git host is GitHub. The agent engine is Claude, through the Claude Agent SDK.
> - Hewn itself is built with a .NET backend (ASP.NET Core with SignalR) and an Angular frontend.
> - Greenlit (`github.com/QuinntyneBrown/greenlit`, default branch) is the skill source.
> - All UI design (stages 2 and 3) is done in Magic Patterns through its MCP server.

---

## L2-001: Submit a product direction
**Traces to:** L1-001

An Owner creates a project by submitting a product direction: a project name, an idea, an optional stack preference and an optional existing GitHub repository.

**Acceptance Criteria:**
1. Given an authenticated Owner on the New direction page with New product selected, when they submit a name of 1–100 characters that is unique among their projects and an idea of 10–20,000 characters, then a project is created, a direction is queued with stage 0 Pending, and the browser navigates to the project page within 2 seconds.
2. Given the name is empty, longer than 100 characters, or already used, when the Owner submits, then nothing is created and an inline error names the field and the rule broken.
3. Given the idea is shorter than 10 or longer than 20,000 characters, when the Owner submits, then nothing is created and an inline error states the allowed length.
4. Given an existing repository URL that is not a `https://github.com/{owner}/{repo}` URL, or a repository the GitHub credential cannot write to, when the Owner submits, then nothing is created and the error explains which.
5. Given a Viewer, when they open the New direction page or POST to the create endpoint, then the page shows "You don't have permission" and the API returns 403.

## L2-002: Projects list
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given projects exist, when a user opens Projects, then each project shows its name, current stage, status (Running, Idle, Paused, Blocked, Cancelled, Complete), percent complete, spend to date and last activity time, sorted by last activity, newest first.
2. Given the user selects a status filter, when the list refreshes, then only projects with that status are shown, and the filter survives a page reload (query string).
3. Given no projects exist, when an Owner opens Projects, then an empty state is shown with a "New product" action. A Viewer sees the empty state without the action.
4. Given a project's status changes, when the list is open, then the row updates in place within 1 second without a reload (L2-031).

---

## L2-003: Archive and delete a project
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given a project with no active direction, when the Owner archives it, then it leaves the default list, appears under the Archived filter, and can be restored.
2. Given a project with an active direction, when the Owner tries to archive or delete it, then the action is refused with "Cancel the running direction first".
3. Given the Owner chooses Delete, when they type the project name exactly and confirm, then Hewn's records, logs and stored artifacts for the project are removed, and the GitHub repository is left untouched. The dialog states that the repository is kept.

---

## L2-004: Run a product direction through every stage
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a queued product direction, when a worker picks it up, then stages 0 to 10 run in order, and each stage starts only after the previous stage has status Succeeded.
2. Given any stage, when its status is shown, then it is exactly one of Pending, Running, Paused, Succeeded, Failed, Skipped, Cancelled. Paused applies to the active stage of a Paused direction, and Cancelled to the active stage of a Cancelled direction.
3. Given every stage succeeds, when stage 10 merges its last non-deferred increment, then the direction is Complete and the project is Idle.
4. Given a project, when a second direction is submitted while one is active, then it queues and starts only when the active one is Complete or Cancelled (one active direction per project, first in, first out).

---

## L2-005: Run a feature direction on an existing product
**Traces to:** L1-002

An Owner submits a feature description (10–20,000 characters) on a project whose first product direction is Complete.

**Acceptance Criteria:**
1. Given a feature direction, when it runs, then stages 0, 4 and 6 are marked Skipped, and stages 1, 2, 3, 5, 7, 8, 9 and 10 run in order, each limited to the new or changed scope.
2. Given the feature has no user interface change (decided and recorded per L2-054), when it runs, then stages 2 and 3 are Skipped.
3. Given a feature direction, when stage 5 runs, then existing L1/L2 IDs are kept, and new requirements take the next free numbers.
4. Given a project whose first product direction is not Complete, when the Owner submits a feature direction, then it is queued behind it (L2-004 AC4).

---

## L2-006: Stage failure and retry
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a run fails, when it is retried automatically, then it is retried up to 3 times with backoff of 30 s, 2 min and 10 min.
2. Given the 3rd retry fails, when the stage ends, then the stage is Failed, the direction is Blocked, an event is pushed to Mission Control with the failure reason and the last 200 log lines, and other projects keep running.
3. Given a Blocked direction, when the Owner presses Retry stage, then the failed stage runs again from its start with its retry counter reset.

## L2-007: Copy skills from Greenlit
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given stage 0 runs, when Greenlit is reachable, then every file under Greenlit's `.claude/skills/` and `.agents/skills/` is copied to the same paths in the target repository and committed as "Bootstrap skills from greenlit@{short-sha}".
2. Given stage 0 completes, when the repository is inspected, then `.hewn/skills.lock` exists and records the source repository URL, the full commit SHA and the list of copied skill names.
3. Given the target repository already has a skill folder with the same name, when stage 0 runs, then that folder is left unchanged and listed in the run log as "kept existing".
4. Given Greenlit cannot be reached, when stage 0 runs, then the run fails with "Greenlit unreachable" and is retried per L2-006.

## L2-008: Update a project's skills
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given Greenlit's default branch is ahead of the SHA in `.hewn/skills.lock`, when an Owner loads the project page, then it shows "Skills update available ({n} commits)". Viewers do not see it, because they cannot act on it.
2. Given the Owner chooses Update skills, when the update runs, then a pull request updates the skill files and `.hewn/skills.lock`, and it merges automatically when checks pass (L2-025).

## L2-009: Produce the product brief
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given stage 1 runs, when it completes, then `docs/brief.md` exists with the non-empty sections Problem, Users, Core features, Out of scope and Assumptions.
2. Given stage 1 runs the `grilling` skill, when the skill poses a question, then the agent answers it itself (L2-054), and each question and answer appears in the run log.
3. Given `docs/brief.md` is missing a required section, when stage 1 validates its output, then the run fails.

## L2-010: Design the screens in Magic Patterns
**Traces to:** L1-005

All UI design is done in Magic Patterns (magicpatterns.com) through its MCP server. Agents do not hand-write mocks.

**Acceptance Criteria:**
1. Given stage 2 runs, when the agent designs screens, then it creates and edits them in Magic Patterns through the Magic Patterns MCP server, guided by the `writing-html-mocks` skill's screen inventory and state rules.
2. Given stage 2 completes, when the project is inspected, then every core feature in the brief maps to at least one Magic Patterns design, and each design's Magic Patterns URL is recorded in `docs/mocks/manifest` along with its screen and state.
3. Given the designs, when stage 2 exports them, then a static HTML export of every screen and state is committed to `docs/mocks/` so later stages and tests work from files in the repository.
4. Given the exported mocks, when stage 2 validates them, then every HTML file parses, and every screen renders at 375, 768 and 1280 px with no horizontal scroll. Every screen must also have default, loading, empty and error states, or a recorded reason why a state does not apply. Any failure fails the run.
5. Given the Magic Patterns MCP server is unreachable or rejects the credential, when stage 2 runs, then the run fails with "Magic Patterns unavailable: {reason}" and retries per L2-006. Agents never fall back to hand-written mocks.
6. Given a feature direction with UI changes, when stage 2 runs, then existing Magic Patterns designs are updated, or new ones are added, and the export in `docs/mocks/` is refreshed.

## L2-012: Extract the design system
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given stage 3 runs with `extracting-design-systems` on the exported Magic Patterns mocks, when it completes, then `docs/design-system/` contains tokens for colour (light and dark), typography, spacing, radius, elevation and motion, plus one page per component.

4. Given a project with a design system, when a user opens Design system in Mission Control, then the token and component pages can be browsed in the same sandboxed preview as L2-011.

2. Given a direction that names a stack, when stage 4 runs, then that stack is chosen.
3. Given stage 4 completes, when the repository is inspected, then `docs/adr/0001-stack.md` exists with Context, Decision, Alternatives and Consequences sections.

## L2-014: Generate requirements
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given stage 5 runs with `engineering-requirements`, when it completes, then `docs/specs/L1.md` and `docs/specs/L2.md` exist.
2. Given the requirements, when stage 5 validates them, then every L2 traces to an existing L1, every L1 has at least one L2, every L2 has at least one Given/When/Then criterion, and IDs are unique. Any violation fails the run and lists the offending IDs.
3. Given requirements text, when validated, then it contains none of the words "should", "may" or "might" outside quoted text.
4. Given existing requirements, when stage 5 runs again for a later direction, then every existing L1 and L2 ID is kept, and new requirements take numbers above the highest existing one. A dropped or renumbered ID fails the run and names it.

## L2-019: Descope automatically
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given a design estimated at more than the descope threshold (3 ideal days by default, set by an Owner in Settings), when stage 9 runs, then the agent first tries to split it into designs of 3 days or less. If that fails, the design is descoped.
2. Given a design whose L2s appear in no journey's main path, or which the brief lists as out of scope or nice-to-have, when stage 9 runs, then it is descoped.
3. Given a design is descoped, when stage 9 completes, then it appears under "Deferred" in `docs/estimates/README.md` with its reason, and its L2s in `docs/specs/L2.md` gain the line `**Status:** Deferred ({reason})`.
4. Given deferred items, when a user opens the project's Backlog in Mission Control, then they are shown apart from the active backlog, with their reasons.

## L2-020: Order the backlog
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given stage 9 completes, when the backlog is produced, then each increment covers one journey, or one part of a journey, with its L2 IDs, ordered by journey number, and no increment comes before an increment it depends on.
2. Given the backlog, when a user opens Backlog, then each increment shows its status (Queued, In progress, Blocked, Merged, Deferred), its estimate and a link to its pull request once one exists.

## L2-021: Write the tests first
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given an increment starts, when the agent begins, then it creates the branch `feature/{increment-slug}` from the latest default branch.
2. Given the branch, when the first commit is made, then it contains only acceptance tests, each test file starting with a `Traces to: L2-xxx` header comment naming L2s in the increment.
3. Given the test commit, when the new tests run, then at least one fails. The failing result is recorded on the increment ("red recorded"). If all pass, the increment is flagged "tests passed before implementation" in the PR Notes.

---

## L2-022: Implement until green
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given failing acceptance tests, when the agent implements, then the increment is done only when backend tests, frontend lint and unit tests, the increment's acceptance tests and the full e2e suite pass locally in the worker.
2. Given 10 implement-and-test iterations pass without all tests green (configurable), when the 10th ends, then the increment is Blocked with its failing tests listed, and the agent moves to the next increment that does not depend on it.

## L2-023: Record the increment video
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given an increment passes its tests, when the video step runs with `creating-videos`, then a captioned 1080p MP4 of 3 minutes or less, walking through the increment's journey in the running app, is saved under `docs/videos/{increment-slug}/` along with its script.
2. Given the video, when the PR is opened, then the PR body links to it, and Mission Control plays it on the increment page.
3. Given video generation fails, when the step ends, then the increment continues to PR with "Video failed: {reason}" in the PR Notes, and the video step is not retried more than once.

## L2-024: Open the pull request
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given an increment ready for PR, when it is opened, then the title is "{journey title} (journey {n}, L2-xxx[, L2-yyy])".
2. Given the PR body, when it is opened, then it has the sections What, Design and decisions, API, Tests, Deferred and Notes, lists the test commands with pass counts, and ends with the Hewn attribution line.
3. Given a PR is opened, when Mission Control is open, then the increment shows the PR link and live check status within 1 second of the event (L2-031).

---

## L2-025: Merge automatically
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given all required checks pass on the PR, when the last check succeeds, then the PR is squash-merged with no human approval and the branch is deleted.
2. Given the default branch moved since the branch was made, when the agent prepares to merge, then it rebases, re-runs checks, and resolves conflicts itself for up to 3 attempts. After that, the increment is Blocked.
3. Given a required check fails, when the agent sees the failure, then it treats it as a failed iteration under L2-022 AC2.
4. Given a merge, when it completes, then the project's percent complete and `docs/estimates/` are updated before the next increment starts.

---

## L2-026: Worker loop
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given a worker starts with a valid worker token, when it connects, then it registers with an ID, location (Local or Cloud), host name and version, and appears in Mission Control's Workers view within 2 seconds.
2. Given queued work, when a worker is free, then it leases one run, sends a heartbeat every 10 seconds, and holds the lease only while heartbeats arrive.
3. Given a worker stops heartbeating for 60 seconds, when the lease expires, then the run is offered to another worker and resumes from its last checkpoint (L2-050).
4. Given a project, when runs are leased, then at most one worker holds a lease for that project at a time.
5. Given no queued work, when a worker is idle, then it waits for a push from the server, falling back to polling no more than every 15 seconds, and uses under 1% CPU.

---

## L2-027: Same behaviour locally and in the cloud
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given the worker, when it is packaged, then one container image runs either on a developer machine (Docker) or in the cloud, and the location is set only by configuration.
2. Given the same direction and repository, when it runs on a Local worker and on a Cloud worker, then the same stages, validations and outputs are produced.
3. Given a Local worker, when it connects, then it uses outbound connections only, needing no inbound ports on the developer machine.

---

## L2-028: No approval steps
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given a product direction is submitted, when it runs to Complete, then no stage, PR or merge waits for human input. An automated end-to-end test proves this by submitting a small direction and asserting it completes with no user interaction after submission.
2. Given any stage, when it would normally ask a human (a skill question, a review or a PR approval), then it proceeds under L2-054 instead.

---

## L2-029: Pause, resume, cancel and stop all
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given a running direction, when the Owner presses Pause, then the current step finishes, the direction becomes Paused, and nothing new starts until Resume.
2. Given a paused direction, when the Owner presses Resume, then work continues from the next step.
3. Given a running or paused direction, when the Owner presses Cancel and confirms, then the active run stops within 10 seconds, the direction is Cancelled, and open PRs are left open and labelled `hewn:cancelled`.
4. Given the Owner presses Stop all workers and confirms, when the command is sent, then every worker halts its active run within 10 seconds and leases no new work until the Owner presses Start workers.
5. Given a Viewer, when they try any of these actions, then the controls are hidden and the API returns 403.

## L2-030: Project page
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given a project, when a user opens it, then a pipeline shows every stage with its status, duration and an icon plus a text label for each status (never colour alone).
2. Given a stage is Running, when its status is shown, then the current step and the latest log line are visible and update live.
3. Given a stage, when the user selects it, then its runs, logs, artifacts and decisions (L2-054) are shown.

## L2-031: Real-time events
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given a stage status change, log line, artifact, PR, check status, spend update or worker status change, when it happens, then a SignalR event reaches subscribed clients with a p95 latency of 1 second or less.
2. Given each event, when it is sent, then it carries a per-project sequence number that increases by one.

---

## L2-032: Reconnect without losing events
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given the SignalR connection drops, when the client notices, then it shows a "Reconnecting…" banner and retries after 0, 2, 10 and 30 seconds, then every 30 seconds.
2. Given the client reconnects, when it resubscribes, then it fetches every event after its last sequence number, applies each once, and the screen matches a fresh page load.
3. Given the connection comes back, when catch-up finishes, then the banner disappears.

## L2-033: Live log stream
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given a running run, when a user opens its log, then new lines appear as they arrive, and the view follows the newest line.
2. Given the user scrolls up, when new lines arrive, then the view stays where it is and shows "{n} new lines — Jump to latest".
3. Given a log of more than 5,000 lines, when it is displayed, then it is virtualized, so no more than 500 line elements are in the DOM at once.

## L2-037: Check status
**Traces to:** L1-018

**Acceptance Criteria:**
1. Given an open PR, when a check changes state, then Hewn learns of it through a GitHub webhook, or through polling every 60 seconds if no webhook arrives, and emits an event (L2-031).

## L2-038: Authentication
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given an unauthenticated request, when it targets any page, API or hub other than `/health/*` and the GitHub webhook, then pages redirect to sign-in and APIs and hubs return 401.
2. Given a user signs in with GitHub, when their GitHub account is not on the Hewn allow list, then sign-in is refused with "This account doesn't have access".
3. Given a session, when it is 8 hours old or the user signs out, then it ends, and later requests are treated as unauthenticated.
4. Given the session cookie, when it is set, then it is `HttpOnly`, `Secure` and `SameSite=Lax`.
5. Given an Owner, when they open Settings, then they can add a GitHub login to the allow list as Owner or Viewer, or remove one, and a Viewer sees the list read-only.

---

## L2-039: Authorization
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given a Viewer, when they call any endpoint that changes state, then the server returns 403, whatever the client shows.
2. Given a user, when they request a project or join a hub group for a project they cannot access, then the server returns 404 or refuses the group, without revealing that the project exists.

---

## L2-040: Secrets
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given model API keys, Magic Patterns credentials, GitHub App keys and worker tokens, when they are stored, then they are encrypted at rest (a cloud key vault in the cloud, the OS key store locally) and no API response ever contains them.
2. Given a log line, event or PR body, when it contains a value matching a stored secret or a known token pattern (GitHub, Anthropic, Azure), then the value is replaced with `***` before it is stored or sent.
3. Given an agent workspace, when a run ends, then credentials written into it are deleted.

---

## L2-041: Worker authentication
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given an Owner, when they create a worker token, then the token is shown once and only its hash is stored.
2. Given a token is revoked, when its worker is connected, then the worker is disconnected within 10 seconds and its lease is released.
3. Given an Owner creates a token, when they choose an expiry of 30 days, 90 days or 1 year, then the token stops working at that time.

---

## L2-042: Agent isolation
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given a run, when it starts, then it runs in its own container and workspace, with no access to other projects' workspaces or to the host's files and credentials.
2. Given a run, when it makes network requests, then only GitHub, the model API, the Magic Patterns MCP server and the stack's package registries are allowed. Other requests are blocked and logged.
3. Given a stage, when the agent calls a tool not on that stage's allow list, then the call is denied and logged as a security event.
4. Given content the agent reads from repositories, mocks, or the web, when it contains instructions, then the agent cannot change Hewn configuration, budgets, secrets or another project, because no tool exposes them.

---

## L2-043: Input validation and web protections
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given any API input, when it fails server-side validation, then the server returns 400 with field errors and makes no change.
2. Given Mission Control pages, when they are served, then they carry a Content-Security-Policy with no `unsafe-inline` scripts, plus `X-Content-Type-Options: nosniff` and `frame-ancestors 'self'`.
3. Given state-changing requests, when they arrive without a valid anti-forgery token, then they return 400.
4. Given an Owner, when they submit more than 10 directions in a minute, then the extra requests return 429.
5. Given the OWASP ZAP baseline scan, when it runs in CI, then it reports no High findings.

---

## L2-044: Audit log
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given a sign-in, direction submission, pause, resume, cancel, stop all, start workers, token creation or revocation, or merge, when it happens, then an audit entry records who did it, what, when and from which IP. Entries cannot be edited through any API.
2. Given an Owner, when they open Audit, then entries are listed newest first and can be filtered by project and action.

---

## L2-045: Performance targets
**Traces to:** L1-020

**Acceptance Criteria:**
1. Given a mid-tier phone on a 4G profile (Lighthouse mobile), when Mission Control's Projects page loads, then Largest Contentful Paint is 2.5 s or less, and the initial JavaScript is 500 KB gzipped or less.
2. Given 50 projects and 20 connected workers, when the read APIs are load-tested, then p95 response time is 300 ms or less.
3. Given 200 events per second across all projects, when clients are subscribed, then the latency target in L2-031 AC1 still holds.

---

## L2-046: Responsive layout
**Traces to:** L1-021

**Acceptance Criteria:**
1. Given XS (<576 px), when any page renders, then content is one column, navigation collapses into a menu, and the pipeline is a vertical list.
2. Given S (≥576 px) and M (≥768 px), when the project page renders, then the pipeline is a horizontal, scrollable stepper above the stage detail.
3. Given L (≥992 px) and XL (≥1200 px), when any page renders, then navigation is a fixed sidebar, and the project page shows the pipeline and the stage detail side by side.
4. Given any width from 320 to 2560 px, when any page renders, then there is no horizontal page scroll, and touch targets are at least 44×44 px.

## L2-047: Accessibility
**Traces to:** L1-021

**Acceptance Criteria:**
1. Given every page in every state, when axe-core runs in the e2e suite, then there are no serious or critical violations.
2. Given a keyboard-only user, when they use any feature, then everything can be reached and used with a visible focus indicator and no keyboard traps.
3. Given stage status changes, when they occur, then they are announced through a polite live region, at most once every 5 seconds per project.
4. Given the user prefers reduced motion, when animations would play, then they are disabled.

2. Given the user picks Light, Dark or System, when they reload, then their choice is kept, and text contrast meets 4.5:1 in both themes.

## L2-049: Logs, metrics and traces
**Traces to:** L1-022

**Acceptance Criteria:**
1. Given any server or worker log entry, when it is written, then it is structured JSON with timestamp, level, message, and project, direction, stage, run and trace IDs where they apply.
2. Given a run, when it executes, then OpenTelemetry traces span the API, the queue, the worker and model calls under one trace ID.
3. Given the platform, when metrics are scraped, then stage duration, stage success rate, queue depth, active workers, event latency, tokens and spend are exported.

## L2-050: Durable state and recovery
**Traces to:** L1-022

**Acceptance Criteria:**
1. Given a direction, run or event, when the API acknowledges it, then it has already been persisted to the database.
2. Given the server restarts during a run, when it comes back, then no direction is lost, and every lease is either kept by its worker's next heartbeat or expires per L2-026 AC3.
3. Given a run is resumed after a crash, when it restarts, then it continues from its last checkpoint (the end of the last completed step, committed to the branch). No completed step runs twice.

**Traces to:** L1-022

**Acceptance Criteria:**

2. Given the server, when `/health/ready` is requested, then it returns 200 only when the database and SignalR backplane are reachable, and 503 otherwise.

**Acceptance Criteria:**

2. Given a project or direction, when a user views it, then the spend to date is shown and updates live (L2-031).

## L2-053: Budgets
**Traces to:** L1-023

**Acceptance Criteria:**
1. Given a direction, when it is submitted, then it has a budget (the default budget an Owner sets in Settings, which the Owner can change when submitting).
2. Given spend reaches 80% of the budget, when it crosses the threshold, then a warning event is pushed and shown on the project.
3. Given spend reaches 100%, when it crosses the threshold, then the direction is Paused with the reason "Budget reached" after the current model call. It resumes only when the Owner raises the budget above the spend so far and resumes it, in one action (Raise and resume). This is a safety stop, not an approval step (L2-028).

## L2-054: Agents decide and record decisions
**Traces to:** L1-024

**Acceptance Criteria:**
1. Given a skill or stage asks a question meant for the user, when the agent meets it, then it answers from the direction, the brief and the existing artifacts, and carries on without waiting.
2. Given each such decision, when it is made, then it is appended to `docs/decisions.md` with the date, stage, question, answer and rationale. A decision that changes architecture also gets an ADR in `docs/adr/`.
3. Given a project, when a user opens Decisions in Mission Control, then decisions are listed newest first, can be filtered by stage, and link to the commit that recorded them.
