# L1 - High-Level Requirements

> Status: DRAFT v2 — autonomy decision applied (no human approval after direction is given).
>
> Hewn is a software factory. Autonomous agents, running in a continuous loop on local or cloud infrastructure, carry a software product or feature from a human's direction to merged code through a fixed, ordered pipeline. Once a direction is given, no step waits for human approval. "Mission Control" is the Angular web frontend through which humans give direction and observe the work in real time (SignalR).

## Pipeline Stages (reference)

Greenlit (`github.com/QuinntyneBrown/greenlit`) is the reference product built with this process. Its `.claude/skills/` and `.agents/skills/` folders are the skill library, and its `docs/` layout is the artifact layout every Hewn-built project follows.

| # | Stage | Greenlit skill | Primary output (in the target repo) |
|---|-------|----------------|-------------------------------------|
| 0 | Bootstrap | — | `.claude/skills/` and `.agents/skills/` copied from Greenlit |
| 1 | Idea | `grilling` | Product brief (sharpened by a grilling interview) |
| 2 | HTML Mocks | `writing-html-mocks` + Magic Patterns MCP | Designs in Magic Patterns, exported to `docs/mocks/`: every screen and state, responsive, light/dark |
| 3 | Design System | `extracting-design-systems` | `docs/design-system/` — tokens, foundations, component pages |
| 4 | Stack Selection | — (no skill yet) | Stack decision record in `docs/adr/` (default: .NET backend, Angular frontend) |
| 5 | Requirements | `engineering-requirements` | `docs/specs/L1.md`, `docs/specs/L2.md` |
| 6 | Scaffold | — (no skill yet) | Stack-specific solution and folder structure |
| 7 | Detailed Designs | `writing-software-design-documents` | `docs/detailed-designs/{subsystem}/{feature}/` |
| 8 | User Journeys | — (no skill yet) | `docs/journeys.md` — numbered journeys |
| 9 | Estimates | `estimating-designs` | `docs/estimates/` — estimates, % complete, roadmap, descoped items |
| 10 | Incremental Implementation | `implementing-incrementally`, `writing-feature-prompts`, `creating-videos` | Per increment: Test → Implement → Video (`docs/videos/`) → PR titled "{Journey} (journey N, L2-xxx)" → Merge |

## L1-001: Project Management
The system shall let users create, view, configure, archive, and delete software projects, each representing one product being built by the factory and tracked independently through the pipeline.

## L1-002: Pipeline Orchestration
The system shall accept a direction to build a new product or to add a feature to an existing product, and drive it through the ordered pipeline stages (0–10 for a product, the applicable subset for a feature), tracking the status of every stage, enforcing stage ordering, and retrying failed stages.

## L1-003: Skill Library Bootstrap (Stage 0)
The system shall seed each new project with skills copied from the Greenlit repository (`.claude/skills/` and `.agents/skills/`), recording the Greenlit commit they came from, so that every downstream agent works from a known, versioned set of instructions and projects can later be updated to newer skill versions.

## L1-004: Idea Capture (Stage 1)
The system shall capture a product idea from the user and have agents refine it into a structured product brief.

## L1-005: HTML Mock Generation (Stage 2)
The system shall design every screen and state of the product in Magic Patterns (through its MCP server) from the brief, export them as static HTML mocks into the repository, and let users preview them and open them in Magic Patterns.

## L1-006: Design System Extraction (Stage 3)
The system shall extract a reusable design system (tokens and components) from the approved HTML mocks.

## L1-007: Stack Selection (Stage 4)
The system shall choose a technology stack for the project, defaulting to a .NET backend and Angular frontend unless the direction names a different stack, and record the decision.

## L1-008: Requirements Generation (Stage 5)
The system shall produce traceable L1 and L2 requirements with Given/When/Then acceptance criteria from the approved brief, mocks, and stack.

## L1-009: Project Scaffolding (Stage 6)
The system shall generate a stack-specific solution skeleton and folder structure in the project's source repository.

## L1-010: Detailed Design (Stage 7)
The system shall produce detailed technical designs for each feature, traceable to the L2 requirements they satisfy.

## L1-011: User Journeys (Stage 8)
The system shall define end-to-end user journeys that exercise the requirements and serve as the basis for end-to-end acceptance tests.

## L1-012: Estimation and Descoping (Stage 9)
The system shall estimate the effort for each requirement and increment, flag items that appear excessive in cost or complexity, propose descoping them, and produce an ordered implementation backlog.

## L1-013: Incremental Implementation (Stage 10)
The system shall implement the backlog one increment at a time, where each increment writes failing acceptance tests first, implements code until they pass, records a video demonstrating the working increment, opens a pull request, and merges it automatically once all required checks pass.

## L1-014: Agent Runtime
The system shall run agents in a continuous, resumable work loop that can execute either on the user's local machine or in the cloud, with the same behavior in both environments.

## L1-015: Autonomous Execution with Human Oversight
The system shall carry a direction from submission to merged code with no human approval step. Humans shall be able to observe all work and, as a safety control only, pause, resume, or cancel a direction and stop all agents.

## L1-016: Real-Time Mission Control
The Mission Control frontend shall reflect agent activity, stage progress, logs, and artifacts in real time without manual page refreshes.

## L1-017: Artifact Management and Traceability
The system shall store every stage output as a versioned artifact and maintain traceability from idea through requirements, designs, tests, code, and pull requests.

## L1-018: Source Control Integration
The system shall integrate with Git hosting to create repositories and branches, push commits, open pull requests, report check status, and merge.

## L1-019: Security
The system shall authenticate all users and agents, authorize every action by role and project, protect secrets and credentials, validate all inputs, isolate agent execution, and defend against the OWASP Top 10.

## L1-020: Performance and Scalability
The system shall deliver responsive UI interactions and low-latency real-time updates, and scale to many concurrent projects and agents.

## L1-021: Responsive and Accessible UI
Mission Control shall be usable across extra-small through extra-large viewports and conform to WCAG 2.1 AA.

## L1-022: Observability and Reliability
The system shall emit structured logs, metrics, and traces for all agent and platform activity, and recover from agent, process, or connection failures without losing work.

## L1-023: Cost and Resource Governance
The system shall track and limit AI model usage, compute, and spend per project and per agent run, halting work that exceeds configured budgets.

## L1-024: Autonomous Decision Making
Where a skill or stage would ordinarily ask the user a question, agents shall answer it themselves from the direction and existing project artifacts, and record every such decision with its rationale so humans can review it after the fact.
