Pattern

Forms

How Hewn asks for input: one column, labels above, errors under the field and summarised at the top, a single primary action that turns busy while it works.

WCAG 2.2 AA

Overview

Mission Control has few forms, and each one starts something expensive: a direction that spends up to its budget, a worker token, a budget raise that resumes work. So forms are short, every field explains its limit up front, and nothing typed is ever lost to an error.

  • Page forms: New direction is the only one. A .form-col next to a rail that explains what happens after submit.
  • Settings sections: each .settings-section that edits values is its own <form> with its own Save button (Save defaults). Sections that take effect immediately (theme) have no button and say so: Saved immediately.
  • Dialog forms: one to three fields that finish a single action: raise a budget, add a GitHub login, name a worker token.
  • Destructive confirmation: a dialog that asks the person to type the object's name before the danger button enables (Type Harbor CRM to confirm).

The pattern is assembled from Form field, Form layout, Text field, Textarea, Select, Radio group, Switch, Button, Alert and Inline message. Writing rules for labels and errors are in Content.

When to use

SituationUseNot
Starting new work with several inputsA page form with a rail (New direction)A dialog: the idea field needs room, and people paste long text
Changing saved defaultsA settings section form with its own SaveOne Save button for the whole Settings page
A preference that is safe to apply instantlyRadios or a switch with no Save; say Saved immediatelyA Save button that does nothing visible
One to three values that complete an actionA dialog form (Raise budget, Add a GitHub login)Navigating away to a page and back
Deleting something that cannot be restoredAn alertdialog with type-to-confirmA danger button directly on the page (Settings had one; see Button)
Filtering a listInline selects in the page header, applied on change (Audit)A form with an Apply button

  1. Title and consequence: the page heading plus one sentence on what submitting does (Hewn runs to merged code without asking you anything).
  2. Error summary (.callout--danger.form-summary, role="alert", tabindex="-1"): only after a submit. Title counts the problems and names the goal: 3 things to fix before Hewn can start. One link per error, in field order, worded as the problem.
  3. Fields: one column (--layout-form-max). Two short, related fields may pair in .form-grid--2 from sm (Stack and Existing repository). Long text gets a textarea sized to the expected answer.
  4. Hints: the rule before it is broken (1–100 characters, unique among your projects, Pauses at 100%, warns at 80%). When the field errs, the error replaces the hint.
  5. Actions bar (.form-actions): primary first and leftmost on pages, then Cancel as a ghost button. In dialogs the order flips: primary last, on the right (see Dialogs and overlays).

Responsive behaviour

  • Mobile first: one column, full width, inside the page margin (--layout-margin). Controls are 40px tall; the money prefix and inputs never shrink below their text.
  • From sm (36rem) .form-grid--2 puts paired short fields side by side; the page header and its actions sit in a row.
  • From lg (62rem) .split--form adds the rail (What runs next) beside the form with a hairline; below lg the rail follows the form. Settings sections switch to a 16rem intro column beside the body.
  • From xl (75rem) the rail widens to --layout-rail-aside; the form column stays at --layout-form-max so lines stay readable.
  • Dialog forms become bottom sheets below sm with a sticky footer, so Raise and resume is never pushed off screen by the keyboard.
  • Inputs keep 16px text on phones so iOS does not zoom on focus.

Accessibility

Role and pattern

Native <form novalidate> with native controls; the app runs its own validation so the messages follow these rules rather than the browser's. Each settings form is labelled by its section title (aria-labelledby). Radio groups and type pickers are <fieldset> + <legend> (visually hidden when the section title already says it).

Keyboard

KeyAction
TabMoves through fields, then the actions, in visual order.
EnterSubmits from a single-line input. In a textarea it adds a line.
Enter on a summary linkMoves focus into the field with the error (the link targets the control's id).
EscIn a dialog form, closes the dialog and keeps nothing; on a page it does nothing.

Focus and announcements

On a failed submit, focus moves to the error summary (tabindex="-1", role="alert"), so its title and count are read at once. Field errors are linked with aria-describedby and the control gets aria-invalid="true"; the error text starts with the field's subject so it makes sense alone. A busy primary keeps focus (aria-busy + aria-disabled, never disabled). Success in place is a role="status" callout; success that navigates moves focus to the new page's h1.

Labelling

Every control has a visible <label for>; placeholders only show an example or the default (Creates hewn-builds/ledgerline) and never replace the label. (optional) is part of the label text, so it is read. The money prefix is aria-hidden; the label or hint states the currency where it is not obvious.

Touch

Inputs are 40px tall and full width on phones; summary links have a full line of text as the target; actions are 40px buttons with 12px between them.

Content

  • Labels are nouns in sentence case: Name, Idea, Existing repository, Default budget per direction. No colons, no question marks.
  • Hints give the rule and the default: 1–100 characters, unique among your projects; Default: .NET backend, Angular frontend; Pauses at 100%, warns at 80%. Project default is $300.
  • Errors say what is wrong and how to fix it, with the actual number: The idea must be 10 to 20,000 characters. This one has 8.; Default budget must be between $10.00 and $10,000.00.
  • Errors that depend on something outside the form say who can fix it: Hewn’s GitHub App can’t write to northwind/handover. Install the app on that repository, or leave this empty to create one.
  • Summary titles count and name the goal: 3 things to fix before Hewn can start; in Settings, where there is no single goal, 2 things to fix. Summary links are short forms of the field errors.
  • Submit verbs match the outcome: Start direction, Save defaults, Raise and resume, Create token, Add to allow list. The busy label is the progressive form: Queuing direction…, Saving…, Creating token….
  • Mark the optional fields, not the required ones: most fields are required, and (optional) is the rarer, more useful signal.
