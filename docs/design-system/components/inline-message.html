Inline message

Inline messages sit directly under one control: the hint that says what to enter, the error that says what to fix, and the confirmation that a check passed.

WCAG 2.2 AAStatus: stable

Overview

Every Form field can show one or more inline messages below its control. They are part of the field, linked to the control with aria-describedby, and say something about this field only. Messages about the whole form go in an error summary callout; messages about something that happened go in a Toast.

  • Hint (.field__hint): format, limits or a default, shown before any input: Pauses at 100%, warns at 80%. Project default is $300.
  • Error (.field__error): what is wrong and how to fix it, with an icon, after the field is left or the form submitted.
  • Success (.field__success): a server-side check passed (repository access), shown only where a check is not obvious.
  • Counter (.field__counter): characters used against a limit, right-aligned, tabular.

Anatomy

  1. Label.field__label; the control's name.
  2. ControlInvalid: aria-invalid="true" draws the 2px danger ring.
  3. Error.field__error: 14px danger text with a 14px alert icon; first in aria-describedby.
  4. Hint.field__hint: 12px subtle text; stays visible under the error so the rule is not lost.

Sizes

One size: hints and counters use --text-caption (12px), errors and success messages --text-body-sm (14px) so the important ones read first.

Messages follow the field's state. Pointer and focus states are forced with data-state.

  • When errors appear: on leaving a field that has a value, or on submit for every field. Never while typing the first time.
  • When they clear: as soon as the value becomes valid, on input (the person is fixing it, so live feedback helps).
  • Success only follows a check the person cannot see (repository write access); never mark ordinary fields valid.

Responsive behaviour

  • Messages wrap under the control at every width; they never sit beside it, so they cannot be cut off at 360px.
  • In two-column form grids (from sm) each column keeps its own messages; a long error does not push the neighbouring field.
  • The counter is right-aligned under the control at every width.

Theming

Hint and counter read --color-fg-subtle; error --color-danger-strong; success --color-success-fg. All three keep 4.5:1 on surface and canvas in both themes. The invalid ring is --field-invalid (--color-danger-icon), a component token a form can override.

Accessibility

Role and pattern

No widget role: the messages are plain text referenced by the control's aria-describedby (error first, then hint), with aria-invalid="true" on the control while it is in error. See 3.3.1 Error identification and 3.3.3 Error suggestion. A success message from an asynchronous check is inserted into a container with role="status".

Keyboard

KeyAction
TabMessages are not focusable; they are read when the control receives focus.

Focus

An inline error never moves focus. After a failed submit, focus goes to the error summary, whose links move focus to each field.

Labelling

Errors are read as the control's description after its name and value: Name, Field Notes, invalid entry, Name is already used by another project. Pick a different name. 1–100 characters, unique among your projects. Icons are aria-hidden.

Motion

None. Messages appear and disappear in place, without shifting other fields more than their own height.

Touch

Not targets. Keep a 6px gap (--space-1-5) between control and message so a tap on the message is not taken for the control.

Content

  • Errors say what is wrong and how to fix it, with the numbers: The idea must be 10 to 20,000 characters. This one has 8.
  • Give the exact format: Use a https://github.com/{owner}/{repo} URL.
  • When the fix is elsewhere, say where: Install the app on that repository, or leave this empty to create one.
  • Hints state rules and defaults, not instructions to type: Default: .NET backend, Angular frontend.
  • Counters: 312 of 20,000 characters; no remaining.
