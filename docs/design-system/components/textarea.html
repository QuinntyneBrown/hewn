Textarea

Textareas take the long text Hewn builds from: the idea for a new product and the feature for an existing one.

Overview

Use a textarea when the answer is prose that can run to several lines. In Hewn that text is the direction itself: everything downstream (brief, mocks, requirements, increments) is generated from it, so the field is generous, keeps what was typed through every failure, and shows how much room is left. For a single line use a text field.

  • Idea: 7 rows for a new product, with a counter against the 20,000-character limit.
  • Feature: 4 rows for a feature on an existing product.
  • Auto-grow: field-sizing: content grows the box with its text up to a cap, for short optional notes. Browsers without support keep the fixed rows.

Anatomy

  1. Label.field__label, a <label for>.
  2. Text area.textarea: --space-3 padding, --line-height-relaxed, at least two control heights tall.
  3. Resize handleVertical only (resize: vertical); the width follows the column.
  4. Counter.field__counter: right-aligned, tabular, --text-caption; linked with aria-describedby.

Sizes

One height of type; the size is the number of visible rows. Use rows="7" for an idea, rows="4" for a feature, and never fewer than 2 (min-height is two control heights). Width always follows the column.

  • Read-only while the direction is queuing: the text stays selectable and is read in full by screen readers, and the person can scroll it.
  • Invalid shows the count in the error (This one has 8.), so the counter is replaced rather than repeated.
  • Counter updates as the person types and is announced politely, debounced to 500 ms, only within the last 10% of the limit; elsewhere it is read on focus through aria-describedby.

Responsive behaviour

  • Full column width at every breakpoint; the column caps at --layout-form-max.
  • Rows do not change with the viewport: 7 rows is about 13rem on a phone and stays readable without scrolling the page.
  • Below sm the resize handle is still available, but the field also scrolls internally; the page never scrolls sideways.
  • From lg the New direction form sits beside the 20rem plan rail (.split--form); the textarea does not widen past the form column.

Theming

Shares the field component tokens (--field-bg, --field-fg, --field-border, --field-ring, --field-invalid). Long text sits on --color-bg-surface with --line-height-relaxed in both themes so a 300-word idea stays comfortable to proofread in dark.

Accessibility

Role and pattern

Native <textarea> with a visible <label for>; see the W3C forms tutorial. Do not replace it with a contenteditable region.

Keyboard

KeyAction
Tab / Shift + TabMoves into and out of the textarea; Tab never inserts a tab character.
EnterInserts a new line. It never submits the form.
EscNo effect in the field; inside a dialog it closes the dialog, so dialogs with a textarea confirm before discarding text.

Focus

2px inset --field-ring, the same as text fields. After a failed submit (Hewn couldn’t queue this direction) focus goes to the alert, not the textarea, and the text is kept.

Labelling

Visible label; the hint says what to write; the counter is linked after the hint in aria-describedby so it is read on focus. Over the limit, the field is aria-invalid and the error states the count.

Motion

Edge transition over --duration-fast, zeroed under reduced motion. Auto-grow changes height instantly.

Touch

The field is at least 80px tall; a phone keyboard covers part of the screen, so the form keeps the textarea's label in view with scroll-padding-top. Autocorrect and spellcheck stay on for prose.

Content

  • Label with the noun the person is writing: Idea, Feature.
  • Hint says what a good answer contains, not that the field is required.
  • Counter format: 323 of 20,000 characters, tabular, with a thousands separator.
  • Errors give the limit and the current count: The idea must be 10 to 20,000 characters. This one has 8.
  • After a failure, say the text is safe: Nothing was created; your text is kept below.
